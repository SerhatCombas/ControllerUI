# 05_simulation_and_results_requirements.md

## 1. Purpose

This document defines how the Engineering System Designer executes numerical simulations, stores simulation results, and presents time-domain, frequency-domain, and stability-analysis results in the unified results area.

The simulation layer consumes the ODE artifact produced by `04_model_equations_requirements.md`, executes time-domain simulation through the numerical engine, stores results in durable HDF5 files, and exposes result channels to the Result Panel.

This document also defines the Stability Analysis workflow shown in `app_two_module_data_flow.svg`. Stability analysis is not the same concern as time-domain simulation. It is owned by `ControllerDesignModule` because it operates on linearized state-space models and controller-analysis artifacts. The UI uses a unified four-slot Result Panel with grouped plot type dropdowns; stability analysis remains separate at the artifact and ownership level, not as a separate required UI panel.

This document covers:

- simulation request creation
- simulation readiness validation
- solver backend ownership
- CasADi integrator usage
- open-loop simulation flow
- closed-loop controller execution ownership
- initial condition resolution
- output sampling grid semantics
- simulation result artifact structure
- HDF5 result storage
- project result-reference storage
- Result Panel behavior for time-domain, frequency-domain, and algebraic plots
- Stability Analysis Artifact
- stability-analysis plot behavior inside the unified Result Panel
- export requirements
- caching and invalidation rules
- worker-thread execution
- batch UI update strategy
- error handling
- test strategy

This document does not define workspace editing, graph assembly, equation extraction, controller synthesis algorithms, or component library definitions.

## 2. Scope

### 2.1 In Scope

Phase 2 simulation and result handling includes:

- consuming a read-only ODE artifact from `SystemModelingModule`
- consuming simulation settings from `ControllerDesignModule`
- validating simulation readiness
- constructing immutable simulation requests
- executing numerical integration through `shared/engine`
- using CasADi integrators as the primary solver backend
- allowing SciPy solver fallback only behind the engine adapter boundary
- storing full simulation results in HDF5
- storing lightweight result references and summaries in project JSON
- exposing result metadata and signal channels to the Result Panel
- plotting time-domain results
- preserving traceability back to states, inputs, outputs, probes, and I/O selections
- handling failed simulations without corrupting project state
- supporting CSV and PNG export
- defining Stability Analysis Artifact and panel ownership

### 2.2 Out of Scope

The following are out of scope for this document:

- deriving equations from the workspace graph
- DAE reduction and ODE artifact construction
- component equation definitions
- controller tuning algorithms
- LQR / MPC synthesis internals
- pole-placement synthesis internals
- symbolic linearization implementation details beyond artifact ownership
- component library definitions
- workspace command and undo/redo behavior
- real-time hardware-in-the-loop execution
- Phase 2 streaming plots during simulation

## 3. Ownership and Phase Boundary

| Layer | Responsibility |
| --- | --- |
| `SystemModelingModule` | owns workspace, graph, equation extraction, ODE artifact, last valid model snapshot |
| `ControllerDesignModule` | owns controller settings, I/O selection, simulation settings, plot layout, state-space/transfer-function preparation, stability analysis |
| `shared/engine` | owns numerical simulation execution, solver adapters, controller execution adapters, simulation result artifact creation |
| Result UI | renders simulation and stability-analysis artifacts in a unified four-slot panel and exposes plot controls |

### 3.1 Critical Rule

`05_simulation_and_results_requirements.md` starts after a valid ODE artifact exists.

It must not re-derive equations from the workspace graph.

### 3.2 Relationship to 04

`04_model_equations_requirements.md` produces the ODE artifact:

```text
x_dot = f(x, u, t, p)
y     = h(x, u, t, p)
```

The ODE artifact contains:

- state vector metadata
- input vector metadata
- output vector metadata
- parameter metadata
- explicit ODE functions or symbolic expressions
- linearly/time-dependency classification
- validation report
- source workspace hash

The ODE artifact does not contain:

- final `A`, `B`, `C`, `D` matrices
- transfer functions
- Bode data
- poles and zeros
- time-series simulation results
- controller gains generated by design algorithms

### 3.3 Relationship to 03

`03_configuration_requirements.md` owns user-facing configuration state:

- controller settings
- I/O selection
- simulation settings
- plot layout

This document defines how those settings are consumed by simulation and result workflows.

### 3.4 Relationship to 06

`06_data_flow_and_architecture.md` defines the module boundaries and application-level data flow.

This document must preserve the same separation:

- model extraction belongs to `SystemModelingModule`
- controller design and analysis belong to `ControllerDesignModule`
- numerical integration belongs to `shared/engine`

## 4. Simulation Workflow Overview

### 4.1 Default Phase 2 Workflow: Open-Loop Simulation

Phase 2 default simulation is open-loop.

```text
User clicks Run Simulation
→ ControllerDesignModule validates simulation settings and I/O references
→ SystemModelingModule provides current valid ODE artifact
→ SimulationRequest is created
→ shared/engine selects solver backend
→ numerical integration runs in worker thread/process
→ SimulationResultArtifact is created
→ full result data is written to HDF5
→ project JSON stores result reference + summary metadata
→ Result Panel reloads plots from completed result artifact
```

Open-loop simulation means:

- selected inputs are generated from source definitions or user-configured input profiles
- controller outputs do not modify plant inputs
- controller settings may exist but are ignored unless `use_controller = true`

### 4.2 Future Workflow: Closed-Loop Simulation

Closed-loop simulation connects controller execution into the plant input path.

```text
ODE artifact
+ controller settings
+ controller I/O bindings
+ reference signals
+ initial controller state
→ controller execution adapter
→ augmented plant input function
→ numerical integrator
→ simulation result artifact
```

Closed-loop simulation is allowed in Phase 2 only for simple P/PI/PD/PID controllers when the controller wrapper is implemented. Advanced design methods such as LQR and MPC may be configured in the UI, but execution must remain disabled until their runtime adapters are implemented.

### 4.2.1 Controller Execution Ownership Decision

Phase 2 decision:

The controller wrapper lives in `shared/engine/controllers/` as a thin numerical execution adapter.

It receives:

- a controller specification from `ControllerDesignModule`
- controller state, such as integral memory for PI/PID
- current plant state
- current plant output
- reference value
- current time
- effective step interval

It exposes a minimal runtime API:

```text
compute_control(controller_state, y, r, t, dt) -> (u, updated_controller_state)
```

The wrapper is a numerical executor, not a design tool.

It must not contain:

- controller tuning logic
- pole-placement synthesis
- LQR synthesis
- MPC optimization setup
- transfer-function construction
- state-space matrix ownership

Those remain in `ControllerDesignModule`.

This separation keeps:

- control synthesis in `ControllerDesignModule`
- control execution in `shared/engine`
- plant equation generation in `SystemModelingModule`

### 4.3 Simulation Trigger Policy

Simulation is manual.

Workspace edits, parameter edits, and controller setting changes may invalidate prior results, but they must not automatically start a new simulation.

Allowed triggers:

- Run Simulation button
- keyboard shortcut
- future batch test runner
- future scripted automation API

Not allowed in Phase 2:

- automatic simulation on every workspace edit
- automatic simulation on every slider movement
- background solver execution without explicit user action

## 5. Simulation Readiness Validation

### 5.1 Required Inputs

Simulation requires:

- a valid ODE artifact
- valid simulation settings
- valid state vector
- valid input vector or input generation policy
- valid output mapping
- valid parameter values
- no blocking validation errors

### 5.2 Blocking Conditions

Simulation must be blocked when:

- current workspace graph has blocking validation errors
- ODE artifact is missing
- ODE artifact source hash does not match the selected model snapshot
- ODE artifact validation report contains blocking errors
- state vector is empty for a dynamic simulation that requires states
- required parameters are missing or invalid
- initial conditions are missing and cannot be inferred
- explicit initial condition overrides are invalid
- selected solver is unavailable
- selected input references are stale
- selected output references are stale
- `use_controller = true` and controller bindings are invalid
- closed-loop controller type has no runtime execution adapter

### 5.3 Warning Conditions

Simulation may continue with warnings when:

- previous results are stale
- non-selected I/O entries are stale
- unknown future metadata exists but is preserved
- solver falls back from preferred backend to supported fallback
- output channels are valid but some optional plot bindings are stale
- simulation uses last valid model snapshot instead of current invalid workspace

### 5.4 Validation Report

Simulation validation produces a `SimulationValidationReport`.

Recommended schema:

```json
{
  "status": "valid",
  "issues": [
    {
      "severity": "warning",
      "code": "RESULTS_STALE",
      "message": "Existing results were produced from an older workspace hash.",
      "source": {
        "kind": "simulation_result",
        "id": "simres_01HV..."
      }
    }
  ],
  "metadata": {},
  "extensions": {}
}
```

Allowed status values:

- `valid`
- `valid_with_warnings`
- `invalid`

## 6. Simulation Settings Consumption

### 6.1 Time Settings

Simulation consumes time settings from `simulation_settings`.

Required fields:

```json
{
  "start_time": 0.0,
  "stop_time": 10.0,
  "sample_time": 0.01,
  "max_step": null,
  "solver": "auto"
}
```

Rules:

- `start_time` must be numeric
- `stop_time` must be numeric and greater than `start_time`
- `sample_time` must be positive
- `max_step`, if provided, must be positive
- `sample_time` defines storage/output sampling, not necessarily internal solver step size
- solver internal step size may be smaller than `sample_time`

### 6.1.1 Output Grid

`output_grid` defines the time points at which result channels are sampled for storage.

It is independent of the solver's internal step size.

Rules:

- if `output_grid` is empty, a uniform grid is generated:

```text
[start_time, start_time + sample_time, ..., stop_time]
```

- if provided, `output_grid` must be monotonically increasing
- first value must equal `start_time`
- last value must equal `stop_time`
- values may be non-uniform
- duplicate time values are invalid
- values outside `[start_time, stop_time]` are invalid
- solver internal steps may be smaller than the output grid spacing
- only output-grid points are guaranteed to be stored in the result artifact

Non-uniform output grids are useful for:

- logarithmic time sampling
- dense sampling around transients
- sparse long-duration simulations
- user-requested snapshot times

Frequency-domain grids for Bode/Nyquist are not stored in `output_grid`; they belong to `StabilityAnalysisArtifact.frequency_response`.

### 6.2 Solver Settings

Supported Phase 2 solver identifiers:

- `auto`
- `casadi_cvodes`
- `casadi_idas`
- `rk45`
- `bdf`
- `radau`

`auto` selection rule:

- prefer CasADi integrator if available
- select stiff-capable backend for stiff systems when stiffness metadata exists
- otherwise use default non-stiff solver
- emit warning if fallback is required

### 6.3 Initial Conditions

Initial conditions are mapped by stable state identity, not by numeric index.

State matching uses:

```text
(component_id, state_id)
```

Rules:

- numeric vector index is derived only after stable matching
- missing override values fall back to component parameter defaults where available
- user-provided overrides must be unit-compatible
- invalid overrides block simulation
- stale component/state references are preserved and reported

### 6.3.1 Initial Condition Conflict Resolution

When both a component parameter default and an explicit override exist for the same state:

- if `simulation_settings.initial_conditions.source = "component_parameters"`:
  - component parameter is used
  - explicit override is ignored
  - an `info` diagnostic is emitted
- if `source = "explicit_overrides"`:
  - explicit override is used
  - component parameter is used only as fallback when no override exists
- if `source = "merge"`:
  - reserved for Phase 3
  - overrides take precedence
  - component parameters fill gaps

Phase 2 supports only:

- `component_parameters`
- `explicit_overrides`

Unknown source values must be preserved on load but block simulation until resolved.

### 6.4 Input Generation

Input values may come from:

- constant source components
- time-function source components
- external input profiles
- controller outputs in closed-loop mode
- future scripted input generators

Input generation must preserve traceability to the original I/O selection or source component.

### 6.5 Output Selection

Outputs are derived from the ODE artifact output mapping.

Rules:

- outputs must use stable output IDs
- plot bindings must use channel IDs, not array indices
- stale outputs remain visible in configuration as stale but cannot be simulated
- outputs may include port variables, probe values, state variables, or derived expressions

## 7. SimulationRequest

### 7.1 Purpose

`SimulationRequest` is the immutable hand-off object from UI/configuration to `shared/engine`.

It must contain everything needed to reproduce a simulation run.

### 7.2 Schema

Recommended schema:

```json
{
  "id": "simreq_01HV7NE2K8M4Q1W5E7R9T3Y6X9",
  "schema_version": "0.1.0",
  "created_at": "2026-04-27T20:00:00Z",
  "source_ode_artifact_id": "ode_01HV...",
  "source_workspace_hash": "sha256:...",
  "source_settings_hash": "sha256:...",
  "mode": "open_loop",
  "time": {
    "start": 0.0,
    "stop": 10.0,
    "sample_time": 0.01,
    "max_step": null,
    "output_grid": []
  },
  "solver": {
    "id": "auto",
    "options": {}
  },
  "initial_conditions": {
    "source": "component_parameters",
    "values": []
  },
  "inputs": [],
  "outputs": [],
  "controller": null,
  "metadata": {},
  "extensions": {}
}
```

### 7.3 Request Rules

A `SimulationRequest` must:

- be immutable after creation
- include source ODE artifact ID
- include source workspace hash
- include source settings hash
- include deterministic state/input/output ordering
- include solver settings
- include initial conditions
- include selected output channels
- include controller execution configuration only when closed-loop mode is active

A `SimulationRequest` must not:

- mutate workspace state
- mutate controller configuration
- store full result arrays
- reference UI widgets
- depend on array indices without stable metadata

### 7.4 Mode Values

Allowed `mode` values:

- `open_loop`
- `closed_loop`

Future values:

- `parameter_sweep`
- `monte_carlo`
- `optimization_run`
- `hardware_in_loop`

Unknown values must be preserved but not executed.

## 8. Solver Backend Architecture

### 8.1 Engine Boundary

Numerical integration belongs to `shared/engine`.

Expected structure:

```text
shared/engine/
  __init__.py
  simulation_request.py
  simulation_result.py
  solver_registry.py
  solver_adapter.py
  casadi_solver_adapter.py
  scipy_solver_adapter.py
  controllers/
    pid_runtime_adapter.py
  storage/
    hdf5_result_store.py
```

### 8.2 SolverAdapter API

Recommended interface:

```text
SolverAdapter.validate(request, ode_artifact) -> SimulationValidationReport
SolverAdapter.run(request, ode_artifact, progress_callback=None, cancel_token=None) -> SimulationResultArtifact
```

### 8.3 Primary Backend: CasADi Integrators

CasADi integrators are the primary Phase 2 backend.

Reasons:

- consistent with the symbolic backend decision in `04`
- supports automatic differentiation workflows
- suitable for nonlinear ODE workflows
- supports future optimization/MPC direction
- keeps symbolic and numeric hand-off compact

### 8.4 SciPy Fallback Rule

SciPy may be used as fallback inside `shared/engine` only.

Rules:

- SciPy fallback must be hidden behind `SolverAdapter`
- public request/result schemas must not expose SciPy-specific implementation details
- fallback must emit a warning diagnostic
- fallback must not become the architectural contract

### 8.5 Solver Options

Solver options are backend-specific but stored in a generic dictionary:

```json
{
  "solver": {
    "id": "casadi_cvodes",
    "options": {
      "abstol": 1e-8,
      "reltol": 1e-6,
      "max_num_steps": 10000
    }
  }
}
```

Unknown options:

- must be preserved on load
- must be ignored with warning if unsupported by selected solver
- must not crash execution

## 9. Simulation Execution Lifecycle

### 9.1 Lifecycle States

Allowed simulation job states:

- `queued`
- `validating`
- `running`
- `cancel_requested`
- `completed`
- `failed`
- `cancelled`

### 9.2 Worker Requirement

Simulation must not run on the UI thread.

Allowed execution options:

- worker thread
- worker process
- future job queue

The UI must remain responsive during simulation.

### 9.3 Progress Reporting

The engine should emit progress when possible.

Recommended fields:

```json
{
  "job_id": "simjob_01HV...",
  "state": "running",
  "progress": 0.42,
  "message": "Integrating model...",
  "current_time": 4.2,
  "metadata": {}
}
```

### 9.4 Cancellation

The user must be able to cancel long-running simulations.

Rules:

- cancellation should be cooperative
- partial result files must be deleted or marked incomplete
- cancelled simulation must not replace the last successful result
- UI must show cancellation status clearly

### 9.5 Failed Simulation Rule

A failed simulation must:

- not corrupt project state
- not overwrite the last successful result
- not update result references as successful
- preserve error diagnostics
- leave the last valid model snapshot unchanged
- allow the user to inspect the failure report

## 10. Result Channel Model

### 10.1 Channel Types

Simulation results expose channels.

Allowed channel kinds:

- `state`
- `state_derivative`
- `input`
- `output`
- `controller_signal`
- `diagnostic`

### 10.2 Channel ID Policy

Channel IDs must be stable and semantic.

Recommended format:

```text
ch_state_<state_id>
ch_input_<input_id>
ch_output_<output_id>
ch_ctrl_<controller_id>_<signal_id>
ch_diag_<diagnostic_id>
```

Rules:

- plot slots bind to channel IDs
- channel IDs must not depend on array column index
- result files must store channel metadata alongside arrays
- missing channels must be reported as stale plot bindings

### 10.3 Channel Metadata Schema

```json
{
  "id": "ch_state_cmp_01HV_position",
  "kind": "state",
  "display_name": "Mass Position",
  "quantity": "displacement",
  "unit": "m",
  "source": {
    "kind": "state_variable",
    "component_id": "cmp_01HV...",
    "state_id": "position"
  },
  "array_ref": {
    "dataset": "/results/states",
    "column": 0
  },
  "metadata": {},
  "extensions": {}
}
```

### 10.4 Traceability

Every channel must be traceable to at least one of:

- component state
- input variable
- output mapping
- probe
- controller signal
- diagnostic source

## 11. SimulationResultArtifact

### 11.1 Purpose

`SimulationResultArtifact` is the metadata object describing a completed simulation run.

Full numerical arrays live in HDF5.

The artifact contains:

- result identity
- source references
- status
- channel metadata
- storage path
- summary statistics
- validation diagnostics

### 11.2 Schema

```json
{
  "id": "simres_01HV7NE2K8M4Q1W5E7R9T3Y6X9",
  "schema_version": "0.1.0",
  "created_at": "2026-04-27T20:01:00Z",
  "source_request_id": "simreq_01HV...",
  "source_ode_artifact_id": "ode_01HV...",
  "source_workspace_hash": "sha256:...",
  "source_settings_hash": "sha256:...",
  "status": "success",
  "storage": {
    "kind": "hdf5",
    "path": "results/simres_01HV7NE2K8M4Q1W5E7R9T3Y6X9.h5"
  },
  "time": {
    "start": 0.0,
    "stop": 10.0,
    "sample_count": 1001
  },
  "channels": [],
  "summary": {
    "duration_s": 10.0,
    "channel_count": 12,
    "is_stale": false
  },
  "validation_report": {},
  "metadata": {},
  "extensions": {}
}
```

### 11.3 Status Values

Allowed status values:

- `success`
- `failed`
- `cancelled`
- `file_missing`
- `incomplete`

### 11.4 Stale Result Detection

A result is stale when:

- current workspace hash differs from result source workspace hash
- current settings hash differs from result source settings hash
- ODE artifact ID differs from current ODE artifact
- required channels no longer exist

Stale results may still be viewed, but the UI must clearly mark them as stale.

## 12. HDF5 Result Storage

### 12.1 Purpose

HDF5 stores large numerical arrays and a copy of result metadata.

Use:

- `h5py` for direct HDF5 access
- PyTables only if table-style querying becomes necessary

### 12.2 HDF5 Layout

Recommended layout:

```text
/
├── metadata/
│   ├── result_artifact_json
│   ├── simulation_request_json
│   ├── ode_artifact_summary_json
│   └── channel_metadata_json
├── time/
│   └── t
├── results/
│   ├── states
│   ├── state_derivatives
│   ├── inputs
│   ├── outputs
│   ├── controller_signals
│   └── diagnostics
└── logs/
    └── solver_log
```

### 12.3 Dataset Rules

Rules:

- `/time/t` is a 1D array of sampled output-grid time values
- result datasets are 2D arrays shaped `[sample_count, channel_count]`
- columns are mapped through channel metadata
- units are stored in channel metadata, not only dataset attributes
- dataset compression may be enabled for large results
- HDF5 file must contain enough metadata to inspect the result even if project JSON is missing

### 12.4 HDF5 Write Policy

HDF5 writing must be atomic where possible.

Recommended approach:

```text
write temporary file → validate metadata → rename to final result file
```

If writing fails:

- temporary file is removed where possible
- project JSON is not updated as success
- failure diagnostic is shown

### 12.5 Result File Location

Decision: use a project package directory.

A project is stored as a directory bundle:

```text
my_project.systemdesign/
├── project.json
├── results/
│   ├── simres_01HV7NE2K8M4Q1W5E7R9T3Y6X9.h5
│   └── simres_01HW8PZ4N2K1J9A7B5C3D0E1F2.h5
├── recovery/
│   └── autosave.json
└── exports/
    └── plot_01.png
```

Reasons:

- copying the project copies all associated results
- result files stay associated with their source workspace
- the main project JSON remains small and readable
- autosave/recovery files can live beside project data without polluting user folders
- export outputs have a predictable default location

Rejected alternative:

```text
my_project.systemdesign
my_project.results.h5
```

Sibling files are rejected because renaming, moving, or copying only one file breaks the result association.

### 12.6 Cross-Document Impact

This decision affects persistence language in the workspace and architecture documents.

Where older documents say `.systemdesign JSON file`, the Phase 2 interpretation is:

```text
.systemdesign directory bundle containing project.json
```

Migration rule:

- Phase 1 single-file `.systemdesign` projects may be imported
- on first Phase 2 save, the user may be prompted to convert to package format
- original file must remain untouched until conversion succeeds

## 13. Project JSON Result References

### 13.1 Rule

Project JSON stores result references and summary metadata only.

Project JSON must never store full time-series arrays.

### 13.2 Schema

```json
{
  "results": [
    {
      "result_id": "simres_01HV7NE2K8M4Q1W5E7R9T3Y6X9",
      "created_at": "2026-04-27T20:01:00Z",
      "status": "success",
      "source_workspace_hash": "sha256:...",
      "source_settings_hash": "sha256:...",
      "summary": {
        "duration_s": 10.0,
        "sample_count": 1001,
        "channel_count": 12,
        "is_stale": false
      },
      "storage_path": "results/simres_01HV7NE2K8M4Q1W5E7R9T3Y6X9.h5"
    }
  ]
}
```

### 13.3 Rules

- only references and summaries live in JSON
- HDF5 contains full numerical data plus a copy of metadata
- if HDF5 file is missing, JSON entry is preserved with `status: "file_missing"`
- user may purge old results through UI
- purging removes both JSON entry and HDF5 file
- maximum stored result references per project is configurable
- default maximum retained references: `10`
- if the limit is exceeded, UI asks whether to purge old results or keep all

### 13.4 Last Successful Result

The application may track the last successful simulation result:

```json
{
  "last_successful_result_id": "simres_01HV..."
}
```

Rules:

- failed simulations do not replace this pointer
- cancelled simulations do not replace this pointer
- stale results may remain last successful but must be visually marked stale

## 14. Result Panel

### 14.1 Purpose

The Result Panel is the unified visual result area for the application.

It contains four plot slots by default:

1. Time Response
2. Step Response
3. Bode
4. Pole-Zero

The same panel can display plots sourced from either:

- `SimulationResultArtifact` for time-domain simulation data
- `StabilityAnalysisArtifact` for frequency-domain, pole-zero, root-locus, Nyquist, and eigenvalue data

Stability analysis remains a separate artifact and ownership concern, but it does not require a separate UI panel in the approved Phase 2 UI model.

The Result Panel must support:

- 2x2 grid layout
- fullscreen plot view
- per-plot header dropdown
- channel or I/O-pair selection controls
- placeholders when required artifacts are missing
- export controls

### 14.2 Phase 2 Plot Functionality

Plot types are grouped by data source.

#### 14.2.1 Time-Domain Plots

These plots consume `SimulationResultArtifact`:

- `time_response`
- `state_variables`
- `input_output_signal`
- `road_profile`
- `force`

These plots become functional as soon as a successful open-loop or closed-loop simulation produces a result artifact.

#### 14.2.2 Linearization-Required Plots

These plots consume `StabilityAnalysisArtifact`:

- `bode`
- `nyquist`
- `pole_zero`
- `root_locus`
- `eigenvalue`

These plots require:

- `linearity = "linear"`, or successful linearization at an operating point
- `time_dependency = "time_invariant"` for Bode, Nyquist, and Root Locus workflows
- valid state-space matrices produced by `ControllerDesignModule`

If no `StabilityAnalysisArtifact` exists, the plot slot shows a placeholder with a `Linearize and Analyze` action.

#### 14.2.3 Hybrid Plot

`step_response` may use either:

- `SimulationResultArtifact` from a step input simulation
- `StabilityAnalysisArtifact` for analytical LTI step response

The simulation result is preferred when available because it reflects the actually simulated system, including nonlinear behavior and configured input profiles.

If no matching simulation result exists but a valid LTI stability artifact exists, the analytical step response may be computed from the linearized system.

#### 14.2.4 Plot Availability Logic

When a plot slot's `plot_type` is set:

- if the required artifact exists and matches the slot's `channel_selection`, the plot is rendered
- if the required artifact is missing, a placeholder appears with a clear action button
- if the selected channel, input, or output is stale, a warning appears instead of crashing
- the plot type dropdown remains selectable regardless of artifact availability
- missing artifacts must never silently change the user's selected plot type

### 14.3 Default Plot Slots

The Result Panel contains four plot slots by default.

Default slot layout:

| Slot | Default plot type | Selection kind | Default title |
| --- | --- | --- | --- |
| `plot_1` | `time_response` | `channels` | Time Response |
| `plot_2` | `step_response` | `io_pair` | Step Response |
| `plot_3` | `bode` | `io_pair` | Bode |
| `plot_4` | `pole_zero` | `system_wide` | Pole-Zero |

This default aligns with `03_configuration_requirements.md` §8 and preserves the approved four-plot UI decision.

### 14.4 Plot Slot Binding

Each plot slot stores:

```json
{
  "slot_id": "plot_1",
  "plot_type": "time_response",
  "title": "Time Response",
  "channel_selection": {
    "kind": "channels",
    "channels": ["ch_output_y_0"],
    "io_pair": null
  },
  "result_ref": "simres_01HV7NE2K8M4Q1W5E7R9T3Y6X9",
  "analysis_ref": null,
  "axis_config": {
    "x_label": "Time [s]",
    "y_label": null,
    "x_range": null,
    "y_range": null
  },
  "metadata": {},
  "extensions": {}
}
```

Field semantics:

- `slot_id`: stable plot slot identifier, for example `plot_1`
- `plot_type`: selected plot type
- `title`: user-visible title
- `channel_selection`: structured selection defined in `03_configuration_requirements.md` §8.6
- `result_ref`: ID of the `SimulationResultArtifact` used for time-domain plots; `null` if not applicable
- `analysis_ref`: ID of the `StabilityAnalysisArtifact` used for frequency-domain or algebraic plots; `null` if not applicable
- `axis_config`: optional axis configuration

Rules:

- plot slots reference result channels by channel ID, not array indices
- missing channel references display a warning instead of crashing
- changing plot layout marks the project dirty
- new simulation results may auto-bind to default plot slots if no user override exists
- `result_ref` and `analysis_ref` are stale-detected through workspace hash, settings hash, and artifact ID comparison
- full numerical data remains in HDF5 or the relevant analysis artifact; plot slots store only references and selection metadata

### 14.5 Header and Advanced Controls

Each plot slot header should show:

- title (current plot type name, e.g., `Time Response`, `Bode`, `Pole-Zero`)
- a small caret icon (downward chevron `▾` or equivalent) next to the title indicating the title is interactive
- plot type dropdown (opened by clicking title or caret)
- channel or I/O-pair selection control, depending on `channel_selection.kind`
- export button
- optional advanced controls revealed on hover

For full visual specification of the header dropdown control, see `03_configuration_requirements.md` §14.4.1.

The plot type dropdown in the header mirrors the Configuration plot dropdown.

Synchronization rule:

- both dropdowns read from and write to the same `plot_layout.slots[i].plot_type` field
- changing one immediately updates the other through `plotLayoutChanged()`
- there is no separate default/current state
- both dropdowns use the same grouping from `03_configuration_requirements.md` §8.5
- widget instances may be different Qt objects but must share model state, not local widget state

Channel selection control behavior:

- `kind = "channels"` → multi-select dropdown of available result channels
- `kind = "io_pair"` → two dropdowns: input selector and output selector
- `kind = "system_wide"` → no channel control shown

Advanced controls may include:

- axis range
- log scale
- line visibility
- downsampling toggle
- cursor/marker toggle

When the plot type changes:

- if the new type's selection kind matches the previous kind, `channel_selection` is preserved
- if the selection kind differs, `channel_selection` resets and the channel control re-renders

This mirrors the behavior defined in `03_configuration_requirements.md` §8.7.

### 14.6 Fullscreen Behavior

The Result Panel supports:

- 2x2 grid layout
- double-click plot to fullscreen
- close button to return to grid
- header always visible
- advanced controls revealed on hover

Fullscreen state may be persisted as view state but is not required for model correctness.

## 15. Plot Types

### 15.1 Time Response

Source: `SimulationResultArtifact`

Selection kind: `channels`

Behavior:

- x-axis uses the `time` channel
- y-axis uses selected result channels
- units are displayed when available
- multiple channels may be shown if dimensions and units are compatible

### 15.2 Step Response

Source: `SimulationResultArtifact` preferred, or `StabilityAnalysisArtifact` fallback

Selection kind: `io_pair`

Behavior:

- if the simulation used a step input matching the selected `io_pair`, simulation results are plotted directly
- otherwise, if a `StabilityAnalysisArtifact` exists, the analytical step response may be computed from the linearized system
- if neither is available, a placeholder is shown

### 15.3 State Variables

Source: `SimulationResultArtifact`

Selection kind: `channels`

Behavior:

- lists all state channels from the result artifact
- user selects which states to plot
- uses the same x-axis as Time Response

### 15.4 Input/Output Signal

Source: `SimulationResultArtifact`

Selection kind: `channels`

Behavior:

- allows mixing input and output channels in the same plot
- useful for visualizing controller error, actuator effort, or measured output response

### 15.5 Road Profile

Source: `SimulationResultArtifact`

Selection kind: `channels`

Behavior:

- domain-specific helper for vehicle dynamics workflows
- filters channels to those marked as road inputs in metadata
- for projects without road inputs, the channel selector shows an empty list and an explanatory placeholder

### 15.6 Force

Source: `SimulationResultArtifact`

Selection kind: `channels`

Behavior:

- domain-specific helper for force and torque visualization
- filters channels to those with `quantity = "force"` or `quantity = "torque"`

### 15.7 Bode

Source: `StabilityAnalysisArtifact`

Selection kind: `io_pair`

Requires:

- `linearity = "linear"`, or successful linearization at an operating point
- `time_dependency = "time_invariant"`

Behavior:

- magnitude in dB and phase in degrees plotted against frequency
- frequency axis defaults to rad/s with logarithmic scale
- requires linearization
- if requirements are not met, placeholder shows `Linearize and Analyze`

### 15.8 Nyquist

Source: `StabilityAnalysisArtifact`

Selection kind: `io_pair`

Requires: LTI system or frozen-time linearization explicitly accepted by the user.

Behavior:

- parametric plot of frequency response in the complex plane
- uses the same selected input/output pair as Bode

### 15.9 Pole-Zero

Source: `StabilityAnalysisArtifact`

Selection kind: `system_wide`

Requires: linearization.

Behavior:

- plots poles and zeros of the linearized system
- highlights stability by pole location
- unit-circle reference for discrete systems is reserved for Phase 3

### 15.10 Root Locus

Source: `StabilityAnalysisArtifact`

Selection kind: `system_wide`

Requires:

- LTI system
- designated controller gain parameter

Behavior:

- requires the user to specify which controller parameter varies
- shows pole movement as gain sweeps
- Phase 3 may extend root locus tooling for MIMO systems

### 15.11 Eigenvalue

Source: `StabilityAnalysisArtifact`

Selection kind: `system_wide`

Requires: linearization.

Behavior:

- shows eigenvalues of the `A` matrix in the complex plane
- highlights stability using the real-part sign

### 15.12 Plot Type Architectural Rules

- Time-domain plots must not require linearization.
- Frequency-domain and algebraic plots must not be computed by `shared/engine` directly.
- Linearization-required plots must consume only `StabilityAnalysisArtifact` from `ControllerDesignModule`.
- Step Response is the only plot allowed to consume both artifact types, with simulation preferred when available.
- Plot type selection is UI state; unavailable data must produce placeholders, not silent plot type changes.

## 16. Stability Analysis Artifact

### 16.1 Purpose

Stability analysis is a separate concern from time-domain simulation.

While simulation produces time-series trajectories, stability analysis produces frequency-domain, eigenvalue, pole-zero, and margin characterizations of the linearized system at a chosen operating point.

The architecture diagram shows Stability Analysis as a separate analysis concern parallel to time-domain simulation. In the approved UI model, this separation is represented by artifact ownership and grouped plot behavior inside the unified Result Panel rather than by a mandatory separate panel.

### 16.2 Ownership

Stability analysis is owned by `ControllerDesignModule` because it operates on linearized models and state-space matrices produced by that module.

`shared/engine` does not compute stability metrics.

Linear algebra computations may use NumPy/SciPy inside `ControllerDesignModule` through analysis services.

Recommended internal services:

```text
features/ControllerDesignModule/
  analysis/
    linearization_service.py
    state_space_builder.py
    transfer_function_builder.py
    stability_analysis_service.py
    frequency_response_service.py
    root_locus_service.py
```

### 16.3 Required Linearization

Stability analysis requires:

- valid ODE artifact
- valid I/O selection
- valid state-space matrices `A`, `B`, `C`, `D` produced by `ControllerDesignModule`
- valid operating point for nonlinear systems
- `time_dependency = time_invariant` for transfer-function, Bode, Nyquist, and root-locus workflows

Rules:

- if ODE artifact is `linear` and `time_invariant`, zero/default operating point may be used automatically where valid
- if ODE artifact is `nonlinear`, user must select or compute an operating point
- if ODE artifact is `time_variant`, LTI stability tools must be disabled unless an explicit frozen-time linearization is requested
- if system is MIMO, user must select input/output pair for SISO plots or use MIMO-capable views

### 16.4 StabilityAnalysisArtifact Schema

```json
{
  "id": "stab_01HV7NE2K8M4Q1W5E7R9T3Y6X9",
  "schema_version": "0.1.0",
  "created_at": "2026-04-27T20:02:00Z",
  "source_ode_artifact_id": "ode_01HV...",
  "source_workspace_hash": "sha256:...",
  "source_settings_hash": "sha256:...",
  "linearization": {
    "operating_point": {
      "kind": "zero",
      "x0": [],
      "u0": [],
      "parameters": {}
    },
    "state_vector": [],
    "input_vector": [],
    "output_vector": [],
    "A": [[]],
    "B": [[]],
    "C": [[]],
    "D": [[]]
  },
  "eigenvalues": [],
  "poles": [],
  "zeros": [],
  "transfer_functions": [],
  "frequency_response": {
    "omega": [],
    "magnitude": [],
    "phase": [],
    "input_id": null,
    "output_id": null
  },
  "root_locus": {
    "gain_values": [],
    "pole_paths": []
  },
  "stability_assessment": {
    "is_stable": null,
    "is_marginally_stable": null,
    "rightmost_pole_real_part": null,

      "gain_margin_db": null,
```

### 16.5 Matrix Storage Rule

`A`, `B`, `C`, and `D` matrices are allowed inside `StabilityAnalysisArtifact` because this artifact belongs to `ControllerDesignModule`.

They are not allowed inside the ODE artifact produced by `SystemModelingModule`.

This preserves the ownership decision:

```text
04 ODE artifact: no final A/B/C/D
15 Stability artifact: may contain A/B/C/D
```

### 16.6 Persistence Rule

Stability analysis artifacts are lightweight compared with time-series simulation results.

Phase 2 storage rule:

- latest stability artifact may be stored in project JSON as summary + matrices when small
- large frequency-response arrays may be stored in a small HDF5 or JSON artifact under `results/analysis/`
- default behavior: in-memory artifact plus optional project JSON summary

Recommended JSON reference:

```json
{
  "stability_analysis": {
    "last_artifact_id": "stab_01HV...",
    "source_workspace_hash": "sha256:...",
    "status": "success",
    "summary": {
      "is_stable": true,
      "rightmost_pole_real_part": -0.5,
      "gain_margin_db": null,
      "phase_margin_deg": null
    }
  }
}
```

Full persistence of all stability arrays is optional in Phase 2.

### 16.7 Stability Analysis Controls in the Result Panel

Required stability-analysis plot types available in the unified Result Panel:

- Bode magnitude and phase
- Pole-Zero map
- Root Locus
- Nyquist
- Eigenvalue plot

Required user actions:

- select operating point
- choose auto-equilibrium, zero/default, last simulation point, or user-specified operating point
- request linearization
- choose input/output pair for SISO views
- choose plot type from the grouped Result Panel dropdown
- export plot or analysis data

### 16.8 Relationship to Result Panel

The Result Panel is a unified UI surface, but it can render different artifact types.

| Concern | Time-domain plot | Stability-analysis plot |
| --- | --- | --- |
| Source artifact | `SimulationResultArtifact` | `StabilityAnalysisArtifact` |
| Primary owner | `shared/engine` result + UI renderer | `ControllerDesignModule` |
| Computation type | numerical time integration | linear algebra / frequency response |
| Storage | HDF5 | in-memory + project JSON summary, optional analysis file |
| Trigger | Run Simulation | Analyze / Linearize |
| Plot domain | time domain | frequency / eigenvalue domain |
| Examples | x(t), y(t), u(t), diagnostics | Bode, Nyquist, poles, zeros, root locus |

The UI may show these plots side by side in the same 2x2 Result Panel. The artifact boundary remains strict even though the plot surface is shared.

### 16.9 Disabled-State Rules

Stability analysis controls must be disabled when:

- no ODE artifact exists
- ODE artifact has blocking validation errors
- I/O selection is stale
- system is nonlinear and no operating point is selected
- time dependency is incompatible with requested analysis
- selected MIMO input/output pair is invalid
- state-space materialization fails

The UI must explain why analysis is disabled.

Allowed operating point sources:

- `zero`
- `component_initial_conditions`
- `user_specified`
- `last_simulation_initial`
- `last_simulation_final`

### 17.2 Auto-Equilibrium

`auto_equilibrium` attempts to solve:

```text
f(x, u, t, p) = 0
```

Rules:

- owned by `ControllerDesignModule`
- may use CasADi/NumPy/SciPy numerical solving tools
- must produce diagnostics if no equilibrium is found
- must not mutate component parameters
- must not modify the ODE artifact

### 17.3 Last Simulation Operating Points

- result must be successful
- result must not be file-missing
- user must choose initial or final sample, or a specific time sample

## 18. Last Valid Model Fallback

### 18.1 Source

The last valid model snapshot is owned by `SystemModelingModule`.

It is an in-memory fallback model representation.

### 18.2 Simulation Use

If current workspace is invalid and `use_last_valid_model = true`, simulation may use the last valid ODE artifact.

Rules:

- UI must clearly state that the current workspace has errors
- result must be tagged with the snapshot hash, not the current invalid workspace hash
- current invalid workspace must not be silently treated as simulated
- if no last valid model exists, simulation is blocked

### 18.3 Persistence Rule

The last valid model snapshot is not persisted.

Simulation results produced from it may be persisted, but their metadata must identify the exact snapshot hash used.

## 19. Caching and Invalidation

### 19.1 Hashes

Required hashes:

- workspace structural hash
- ODE artifact hash or ID
- simulation settings hash
- input profile hash
- controller settings hash when closed-loop
- solver settings hash

### 19.2 Cache Reuse

A previous result may be reused only when all relevant hashes match.

For open-loop:

```text
workspace_hash + ode_artifact_id + simulation_settings_hash + input_profile_hash
```

For closed-loop:

```text
workspace_hash + ode_artifact_id + simulation_settings_hash + input_profile_hash + controller_settings_hash
```

### 19.3 Invalidation

Results become stale when any relevant hash changes.

Stale results:

- remain viewable
- must be visually marked stale
- must not be used for new controller decisions without warning
- may be purged by user

## 20. Simulation-to-UI Update Strategy

### 20.1 Phase 2 Strategy: Batch Update

Phase 2 uses batch update.

Flow:

```text
worker runs full simulation
→ HDF5 file written on completion
→ project JSON result reference updated
→ UI receives simulation_complete signal
→ Result Panel reloads from HDF5
```

Rules:

- no continuous plot streaming in Phase 2
- no partial HDF5 result is shown as final
- progress bar is shown for long-running jobs
- cancel button is shown for long-running jobs

### 20.2 Future Phase 3 Streaming

Future streaming may add:

- partial result events at intervals
- progressive plot updates
- reservoir-style HDF5 writes
- live solver diagnostics
- pause/resume simulation

Streaming is not in Phase 2 scope.

### 20.3 Long Simulation UX

If wall-clock runtime exceeds 30 seconds, UI should show:

- progress bar where available
- elapsed time
- current simulated time where available
- cancel button
- status message

For typical Phase 2 models under 10 seconds simulated time and around 1000 output samples, batch update is acceptable.

## 28. Summary

This document defines the Phase 2 simulation and results layer.

Core decisions:

- `SystemModelingModule` produces ODE artifacts only.
- `shared/engine` executes numerical time-domain simulation.
- `ControllerDesignModule` owns controller design, state-space materialization, transfer functions, and stability analysis.
- Result Panel is the unified four-slot UI surface for Time Response, Step Response, Bode, Pole-Zero, and future plot types.
- Time-domain plots consume `SimulationResultArtifact`.
- Frequency-domain and algebraic stability plots consume `StabilityAnalysisArtifact`.
- Full simulation arrays are stored in HDF5.
- Project JSON stores lightweight result references and summaries.
- Project storage uses a `.systemdesign/` directory bundle.
- Phase 2 uses batch UI update after simulation completion.

This closes the ownership gap between simulation results and stability analysis while preserving the architecture boundaries established in `02`, `03`, `04`, and `06`, and aligns the plot schema with `03_configuration_requirements.md`.
